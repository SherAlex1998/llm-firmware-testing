# Ручной разбор выживших мутантов (эксперимент 1)

Данные: `results/main_v3`, таблица `analysis/tables/t8_survivors.csv`: 15 из 150 мутантов не убил ни один
валидный тест ни в одном из шести условий. Каждый мутант сверен с исходником модуля (`benchmark/<модуль>/src/logic.cpp`,
номер строки из таблицы). Разбор выполнен 2026-10-19 одним исследователем, второй независимой разметки нет.

Классы проставлены в `SURVIVOR_REVIEW` в `analysis/analyze.py` и попадают в столбцы `review` и `reason` таблицы
`t8_survivors.csv`. Мутанты класса `equivalent` исключаются из пересчёта (`t3_rag_score_adj.csv`,
`t4_rag_mutants_adj.csv`, `t7_operators_adj.csv`); сырые таблицы от разметки не зависят.

| Класс | Мутантов | Смысл | В пересчёте |
|---|---|---|---|
| `equivalent` | 4 | наблюдаемое поведение модуля не меняется | исключены |
| `unobservable` | 2 | отличие есть только внутри одного блокирующего вызова; итоговое состояние и время те же | остаются |
| `needs_signal` | 4 | ловится только замером времени (`millis()`) или сигнала на пине (`pulseIn()`) | остаются |
| `test_gap` | 5 | пропуск в тестах: убивается обычной проверкой пина или вызовом API | остаются |

Влияние на итог: убито 572 из 690 проверок (82.9%) → 572 из 671 (85.2%) без эквивалентных;
если исключить ещё и `unobservable`, получилось бы 572 из 661 (86.5%). Доля убитых по операторам меняется у двух:
off_by_one 48% → 67%, const_change 54% → 66%.

## 1. Эквивалентные (`equivalent`)

**`dc_motor_pot #9`, off_by_one, строка 49.** `if (raw > 1023)` → `if (raw > 1024)`.
Отличие возможно только при `raw = 1024`: оригинал прижимает значение к 1023, мутант нет. Но
`map(1024, 0, 1023, 0, 255)` в целочисленной арифметике равно 261120 / 1023 = 255, как и `map(1023, ...)`. При
`raw > 1024` обе версии прижимают одинаково. Результат `motor_power_from_reading()` совпадает для любого входа.

**`two_color_crossfade #4`, off_by_one, строка 16.** `if (value < 0)` → `if (value < 1)`.
Отличие только при `value = 0`: мутант заходит в ветку и присваивает `value = 0`, то есть то же значение.

**`dual_hbridge #8`, const_change, строка 3.** `g_dir[2] = {0, 0}` → `{1, 0}`.
**`dual_hbridge #9`, const_change, строка 4.** `g_speed[2] = {0, 0}` → `{1, 0}`.
Начальные значения статических переменных. `hb_init()` вызывает `hb_stop_all()`, а та обнуляет `g_dir` и
`g_speed` у обоих моторов, так что после инициализации состояние совпадает. Разницу можно увидеть, только если
вызвать `hb_direction()` или `hb_speed()` до `hb_init()`, а это вне контракта модуля: без `hb_init()` не
настроены даже пины. Эквивалентность здесь условная, при условии корректного использования API.

## 2. Не видны последовательному тесту (`unobservable`)

Тест-скетч выполняется последовательно и видит модуль только между вызовами. Эти мутанты меняют поведение
внутри одного блокирующего вызова, а итоговое состояние и длительность вызова у них те же.

**`railway_gate #9`, drop_call, строка 11.** Удалён `servo.write(pos)` в возрастающем цикле `gate_sweep()`.
Задержки в цикле остаются, после цикла `servo.write(to)` ставит конечный угол. Физически сервопривод прыгает
сразу в конечное положение вместо плавного поворота, но `gate_servo*_angle()` после вызова и время вызова
совпадают.

**`traffic_light #3`, drop_call, строка 60.** Удалён `digitalWrite(TL_PIN_GREEN, LOW)` в цикле `tl_blink_green()`.
Зелёный горит постоянно вместо мигания; после цикла его всё равно гасит `digitalWrite(TL_PIN_GREEN, LOW)`, а
задержки те же. Поймать можно только наблюдением за пином 4 во время вызова (прерывание по таймеру,
логический анализатор, HIL-стенд).

## 3. Нужен замер времени или сигнала (`needs_signal`)

**`railway_gate #6`, flip_cmp, строка 15.** `pos >= to` → `pos < to` в убывающем цикле.
**`railway_gate #8`, flip_cmp, строка 10.** `pos <= to` → `pos > to` в возрастающем цикле.
Условие ложно с первой итерации, цикл не выполняется, и `servo.write(to)` после цикла ставит тот же конечный угол.
Отличие в том, что поворот мгновенный: пропадают 19 шагов по 10 мс на каждый сервопривод. Убивается замером
длительности `gate_open()` / `gate_close()` через `millis()`.

**`traffic_servo_gate #3`, const_change, строка 16.** `attach(TSG_PIN_SERVO, 500, 2500)` → `attach(..., 1000, 2500)`.
`Servo::read()` пересчитывает угол из ширины импульса с тем же минимумом, поэтому `tsg_gate_angle()` возвращает
прежние 0 и 180. Меняется только ширина импульса на пине 10 (1000 мкс вместо 500 мкс для 0°), то есть реальный
угол привода. Убивается измерением импульса через `pulseIn(10, HIGH)`.

**`two_color_crossfade #6`, drop_call, строка 31.** Удалён `analogWrite(XF_PIN_GREEN, g_green)`.
`xf_green_level()` возвращает правильное значение `g_green`, но ШИМ на пине 10 не выставляется. Убивается
проверкой сигнала на пине (`pulseIn()` или регистр `OCR1B`); обычный `digitalRead` для этого не годится, потому
что отключает ШИМ на пине.

## 4. Пропуски в тестах (`test_gap`)

**`dc_motor_pot #6`, drop_call, строка 57.** Удалён `digitalWrite(MOTOR_PIN_IN2, LOW)` в `motor_stop()`.
После `motor_init()` направление «вперёд», и IN2 (пин 13) = HIGH; мутантный `motor_stop()` его не гасит.
Убивается последовательностью `motor_init(); motor_stop(); ASSERT_PIN(13, LOW)`. Тесты проверяли только
`motor_power() == 0`.

**`dual_hbridge #4`, drop_call, строка 38.** Удалён `digitalWrite(b, LOW)` в `hb_forward()`.
Если мотор перед этим ехал назад, IN2 (пин 9) остаётся HIGH. Убивается переходом
`hb_backward(A, ...); hb_forward(A, ...); ASSERT_PIN(9, LOW)`. Тесты проверяли каждое направление с чистого
состояния, но не смену направления.

**`joystick_motor #8`, drop_call, строка 68.** Удалён вызов `jm_apply_axis(analogRead(JM_PIN_AXIS))` в `jm_update()`.
В `avr8js` `analogRead` возвращает 0, поэтому у оригинала `jm_update()` даёт скорость |0 − 512| / 2 = 256 → 255
и направление «против часовой», а у мутанта состояние после `jm_init()` не меняется. Убивается вызовом
`jm_update()` с проверкой `jm_speed()`. Три из четырёх валидных тестов проверяли только `jm_apply_axis()` напрямую.
Четвёртый (GPT-5.6 Terra, RAG on) вызывает `jm_update()`, но проверяет лишь согласованность: скорость в диапазоне
0..255 и пины направления соответствуют `jm_direction()`. Такой слабый оракул не зависит от значения на входе, и
мутант его проходит. Это осознанный компромисс: на плате `analogRead` зависит от положения джойстика, и точная
проверка была бы привязана к симулятору.

**`led_breathing #2`, off_by_one, строка 32.** `return g_velocity > 0` → `return g_velocity > 1`.
Скорость по умолчанию 2, при ней обе версии совпадают. Отличие только при скорости 1:
`breath_set_velocity(1); ASSERT_TRUE(breath_is_rising())`. Граничное значение тесты не проверили.

**`led_chaser #1`, const_change, строка 3.** В `CHASER_PINS` пин 7 заменён на 14 (A0).
Тесты проверяли модуль через `chaser_count_on()` и `chaser_position()`, а `chaser_count_on()` читает пины через тот
же изменённый массив, так что проверка согласна сама с собой. Убивается прямой проверкой пина:
`chaser_light_only(5); ASSERT_PIN(7, HIGH)`. Это пример общей слабости сгенерированных тестов: оракул построен на
данных самого модуля, а не на внешней спецификации.

## Выводы для текста диплома

- Эквивалентные мутанты заметно искажают картину по операторам: «самый трудный» off_by_one оказался таким в
  основном из-за двух эквивалентных мутантов. Сырой и исправленный mutation score стоит приводить вместе.
- Из 11 неэквивалентных выживших 5 — устранимые пропуски в тестах (смена состояния, граничные значения,
  проверка через собственный API), 6 требуют наблюдения за временем или сигналом. Вторая группа — довод в пользу
  аппаратного уровня наблюдения (HIL, логический анализатор) из протокола диплома.
- Ограничение: разметка одного исследователя; эквивалентность обоснована по коду, но не доказана формально.
